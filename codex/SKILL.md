# 一把梭 — 全流程开发管线

> 输入需求 → 规划 → 架构 → TDD 实现 → 审查 → 提交，一条龙。

## 设计哲学

1. **阶段门禁** — 每个阶段完成必须暂停，用户确认后才进入下一阶段
2. **Agent 做重活** — 规划/架构/审查全部委托给对应 agent，主会话负责编排和决策
3. **用户决断** — 你是拍板的人，每个阶段的产出你来审，不合意可以回退重来
4. **失败不蔓延** — 任一阶段不通过，停在当前阶段修复，不继续下一阶段

---

## 工作流（6 阶段）

```
└──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
     ▲              ▲              ▲              ▲              ▲              ▲
     │              │              │              │              │              │
  用户确认       用户确认       用户确认       用户确认       用户确认      git commit
```

## 阶段 0：需求确认

**目标**：把用户的一句话需求拆解为可执行的需求卡片。

### 步骤

1. 理解用户输入，识别模糊点
2. 提出澄清问题（如功能边界、交互细节、异常情况）
3. 确认技术栈和影响范围
4. 输出需求摘要卡片：

```markdown
## 需求卡片

- **标题**: <一句话>
- **类型**: feat / fix / refactor
- **范围**: <影响的服务/模块>
- **验收标准**:
  1. <可验证的条件>
  2. ...
- **约束**: <性能/兼容/安全>
```

5. **暂停，等待用户确认**。用户说"继续"或"没问题"才进入阶段 1。

---

## 阶段 1：规划

**目标**：生成实现计划，分解为可执行的任务列表。

### 步骤

1. 调用 `Agent({ subagent_type: "planner", prompt: "<需求卡片 + 项目上下文>" })`
2. 等待 agent 返回规划结果
3. 向用户展示任务分解、依赖关系和风险点
4. 询问："计划是否 OK？需要调整什么？"
5. **暂停，等待用户确认**。

---

## 阶段 2：架构设计

**目标**：设计技术方案，产出 ADR 和接口契约。

### 步骤

1. 调用 `Agent({ subagent_type: "architect", prompt: "<需求 + 计划 + 要求产出 ADR 格式>" })`
2. 等待 agent 返回架构设计
3. 向用户展示架构决策、接口契约、数据变更
4. 询问："架构方案是否 OK？有无需要调整的设计决策？"
5. **暂停，等待用户确认**。

---

## 阶段 3：TDD 实现

**目标**：测试驱动开发，先测试后实现。

### 步骤

1. 调用 `Agent({ subagent_type: "tdd-guide", prompt: "<需求 + 计划 + 架构方案>" })`
2. 等待 agent 引导 TDD 流程（RED → GREEN → IMPROVE）
3. 确认测试通过且覆盖率 ≥ 80%
4. 向用户展示实现结果和测试报告
5. **暂停，等待用户确认**。

---

## 阶段 4：代码审查

**目标**：并行审查代码质量和安全性。

### 步骤

1. **并行**启动两个 agent：
   - `Agent({ subagent_type: "code-reviewer", prompt: "审查当前变更..." })`
   - `Agent({ subagent_type: "security-reviewer", prompt: "审查当前变更的安全问题..." })`
2. 汇总审查结果，按严重级别列出问题
3. **基础设施配置审查**（主会话执行，agent 不会检查）：
   - 扫描 `src/config/` 目录，识别同概念重复文件（如两个文件定义同一 Provider）
   - NestJS 项目：检查 `nest-cli.json` 的 `assets` 是否覆盖 `src/config/` 下所有 JSON 文件
   - 检查 `.env.example` 变量与 `src/config/` 中 `process.env.*` 引用是否一一对应
   - 检查是否存在硬编码的 API Key/Token/Password（即使在其他文件）
4. CRITICAL 和 HIGH 级别问题**必须修复**后才能继续
5. 修复后重新审查确认
6. 向用户展示审查结论
7. **暂停，等待用户确认**。

---

## 阶段 5：提交

**目标**：生成规范的 commit，打 tag，推送到远端。

### Git 约定

- **命令前缀**：本机主工作目录不含 git 仓库，所有 git 命令用 `git -C <项目路径>` 而非 `cd && git`
- **分支命名**：`类型/YYMMDD_描述`（6 位日期，kebab-case），从 `production` 拉取
- **禁止分支**：`production` / `master` 未经用户明确允许，禁止任何写操作
- **提交格式**：`<type>(<scope>): <中文描述>`
- **敏感文件**：`.env`、credentials、密钥不暂存（`git.mypacelab.com` 内部库例外）
- **冲突处理**：禁止 `git checkout --ours/--theirs`，必须手动审查每个冲突文件
- **误提交恢复**：代码正确不 revert，留在原分支报告用户决断；仅代码有 BUG 才 revert
- **分步任务**：分步执行的任务不提交，所有任务完成后统一提交

### 步骤

1. **提交前验证**（NestJS 项目）：`yarn test && yarn build && yarn format` 全部通过
2. **启动验证**（NestJS 项目）：`npm start` 确认无 DI 错误，通过后停掉进程
3. `git diff --stat` 确认变更范围，检查无敏感文件
4. 按 Conventional Commits 格式生成中文 commit message，展示给用户确认
5. `git add <具体文件>`（不用 `-A`）
6. `git commit -m "message"`
7. 打 tag：`git tag -a vX.Y.Z -m "vX.Y.Z: ..."`（SemVer，注释标签）
8. 询问是否推送：`git push origin <分支> --tags`

## 中断与恢复

- **随时可中断**：每个阶段都有检查点，中断后重新说"继续梭"即可从上次阶段恢复。
- **阶段回退**：用户可以在任何阶段说"回到阶段 X"，重新执行该阶段。
- **跳过阶段**：简单任务可以跳过不必要的阶段（如 bug 修复可能不需要架构设计）。

---

## 适用判断

| 任务类型 | 一把梭？ | 说明 |
|----------|---------|------|
| 新功能开发 | 推荐 | 走完整 6 阶段 |
| Bug 修复 | 简化 | 跳过阶段 1、2，直接 TDD + 审查 + 提交 |
| 重构 | 推荐 | 走完整流程，阶段 2 侧重风险评估 |
| 单文件小改 | 不建议 | 过度流程化，直接改 + 审查即可 |
| 纯研究/调研 | 不适用 | 无代码产出，不需要此流程 |

---

## 反模式警示

- **不要跳过门禁** — 用户确认是安全阀，不要在没有任何确认的情况下连续跑多个阶段
- **不要忽略审查结果** — CRITICAL 级别问题必须修复，不能"先提交后面再改"
- **不要用一把梭处理模糊需求** — 阶段 0 没搞清楚就往下走，后果是 5 个阶段全白跑
- **不要并行执行有依赖的阶段** — 规划和架构可以串行，但架构方案没出来就 TDD 是无意义的
