# 一把梭 — 全流程开发管线

> 输入需求 → 规划 → 架构 → TDD 实现 → 审查 → 提交，一条龙。

## 设计哲学

此版本为 **内联指令版**（纯主会话执行，不依赖外部 agent）。与 Claude Code 版逻辑等价，差异仅在于 Claude Code 版委托 agent 做重活，此版本在主会话内完成所有阶段。

1. **阶段门禁** — 每个阶段完成必须暂停，用户确认后才进入下一阶段
2. **主会话全责** — 所有分析、设计、实现、审查由主会话直接执行
3. **用户决断** — 每个阶段的产出你来审，不合意可以回退重来
4. **失败不蔓延** — 任一阶段不通过，停在当前阶段修复

## 行为红线

1. **编码前思考** — 不确定时提 2-3 种解释，不默默假设
2. **简洁优先** — 最少代码解决问题，不添加未请求的功能
3. **手术刀改动** — 只改任务相关代码，不顺手重构；死代码只提不删
4. **循环验证** — 每阶段定义成功标准，不达标不回；覆盖率 ≥ 80%、CRITICAL=0 是底线

## 语言适配

| 技术栈 | 注入要点 |
|--------|---------|
| Java | JUnit5+AssertJ+Mockito+Testcontainers，p3c，构造器注入，Logback |
| Node.js / NestJS | Vitest+supertest，NestJS分层，pino，`__`私有前缀，Zod |
| Vue / React | Vitest+Testing Library，Pinia/Zustand，Playwright E2E，Prettier+ESLint |

**包管理器检测**（Node.js / 前端项目）：根据锁文件自动选择 — `pnpm-lock.yaml`→pnpm、`yarn.lock`→yarn、`package-lock.json`→npm。优先级：pnpm > yarn > npm。以下文档用 `<pkg>` 指代检测到的包管理器。

## 阶段 0：需求确认

**目标**：把用户的一句话需求拆解为可执行的需求卡片。

### 步骤

1. 理解用户输入，识别模糊点。多子系统**先拆解**，逐个处理
2. 一次只问一个问题澄清（功能边界、交互细节、异常情况）
3. 确认技术栈和影响范围
4. **提出 2-3 种实现方案**，含 trade-off 和推荐理由
5. 输出需求卡片：

```markdown
## 需求卡片

- **标题**: <一句话>
- **类型**: feat / fix / refactor
- **范围**: <影响的服务/模块>
- **验收标准**:
  1. <可验证的条件>
  2. ...
- **约束**: <性能/兼容/安全>
```

6. **暂停，等待用户确认**。

---

## 阶段 1：规划

**目标**：生成实现计划，分解为可执行的任务列表。

### 步骤

1. **先读项目代码**：`Read`/`Bash` 确认项目结构、模块、现有版本
2. 读取项目的 `rules/` 了解语言规范
3. 基于需求卡片 + 项目结构，输出任务分解、依赖关系图、风险点列表
4. 询问："计划是否 OK？需要调整什么？"
5. **暂停，等待用户确认**。

---

## 阶段 2：架构设计

**目标**：设计技术方案，产出 ADR 和接口契约。

### 步骤

1. 基于需求 + 计划，设计架构方案
2. 产出 ADR（决策/后果/替代方案）+ 接口契约 + 数据变更
3. 自检 P0 问题（缺关键决策/接口遗漏/数据变更缺失），至少 3 轮、最多 5 轮
4. 向用户展示架构决策、接口契约、数据变更
5. 询问："架构方案是否 OK？有无需要调整的设计决策？"
6. **暂停，等待用户确认**。

---

## 阶段 3：TDD 实现

**目标**：测试驱动开发，先测试后实现。

**铁律**：没有失败测试 → 没有生产代码。先行代码 = 删除。

### 步骤

1. 先 Read 项目的 `rules/<lang>/testing.md` 了解测试规范
2. 按技术栈编写测试并运行：
   - Java → `mvn test`，JUnit5+AssertJ+Mockito，Testcontainers，JaCoCo
   - Node.js → `<pkg> test`，Vitest+supertest，Playwright E2E
   - 前端 → `<pkg> test`，Vitest+Testing Library，Playwright E2E
3. RED → GREEN → IMPROVE，**目标覆盖率 ≥ 80%**
4. 展示覆盖率。未达 80% → 暂停修复。达标则继续。
5. **暂停，等待用户确认**。

---

## 阶段 4：代码审查

**目标**：全面审查代码质量和安全性。

### 步骤

1. **代码质量审查**（主会话直接检查）：
   - 函数是否聚焦（<50 行）、文件是否内聚（<800 行）、无深度嵌套（>4 层）
   - 错误处理是否显式、命名是否规范
   - 是否有死代码、console.log、调试残留
2. **安全性审查**（主会话直接检查）：
   - 无硬编码密钥/密码/Token
   - SQL 注入防护、XSS 防护、CSRF 保护
   - 输入校验是否完整
3. **基础设施配置审查**：
   - 扫描 `src/config/` 或 `src/main/resources/` 目录，识别同概念重复配置文件
   - NestJS 项目：检查 `nest-cli.json` 的 `assets` 是否覆盖 `src/config/` 下所有 JSON 文件
   - 检查 `.env.example` 变量与代码中 `process.env.*` 引用是否一一对应
   - 检查是否存在硬编码的 API Key/Token/Password
4. CRITICAL 和 HIGH 级别问题**必须修复**后继续，修复前先写复现测试
5. 修复后重新审查确认（至少 3 轮、最多 5 轮）
6. 向用户展示审查结论
7. **暂停，等待用户确认**。

---

## 阶段 5：提交

**目标**：生成规范的 commit，打 tag，推送到远端。

### Git 约定

- **命令前缀**：本机主工作目录不含 git 仓库，所有 git 命令用 `git -C <项目路径>` 而非 `cd && git`
- **分支命名**：`类型/YYMMDD_描述`（6 位日期，kebab-case），从 `production` 拉取
- **禁止分支**：`production` / `master` 未经用户明确允许，禁止任何写操作
- **提交格式**：`<type>(<scope>): <中文描述>`
- **敏感文件**：`.env`、credentials、密钥不暂存
- **冲突处理**：禁止 `git checkout --ours/--theirs`，必须手动审查每个冲突文件
- **误提交恢复**：代码正确不 revert，留在原分支报告用户决断；仅代码有 BUG 才 revert
- **分步任务**：分步执行的任务不提交，所有任务完成后统一提交

### 步骤

1. **启动验证**（NestJS 项目）：运行 `<pkg> start:dev` 或 `npm start`，确认服务能正常启动（无 DI 错误、无 crash），验证通过后停掉进程
2. `git diff --stat` 确认变更范围，检查无敏感文件
3. **格式检查**（按技术栈）：
   - Node.js/前端：`<pkg>` prettier → `<pkg>` eslint → ts-prune（僵尸代码扫描，列清单不自动删）
   - Java：检测 pom.xml 是否含 `maven-pmd-plugin` → 有则 `mvn pmd:check`，无则跳过
4. **构建验证**（Node.js/前端）：`<pkg> build`，构建失败或缺 build 命令 → 暂停
5. **完成前验证**：测试通过 + 覆盖率达标 + 无 CRITICAL/HIGH + 格式已执行 + 构建通过 + 无调试残留
6. 按 conventional commits 格式生成中文 commit message，展示给用户确认
7. `git add <具体文件>`（不用 `-A`）+ `git commit -m "message"`
8. **创建 tag**（feat:/fix: 变更）：根据 type 确定 MAJOR/MINOR/PATCH，打注释标签。非功能变更不创建 tag
9. 询问是否推送：`git push origin <分支> --tags`

## 中断与恢复

- **随时可中断**：每个阶段都有检查点，中断后重新说"继续梭"即可恢复
- **阶段回退**：用户可以在任何阶段说"回到阶段 X"，重新执行
- **跳过阶段**：简单任务可跳过不必要的阶段

## 任务适配

| 任务类型 | 行为 |
|----------|------|
| 新功能开发 | 推荐 — 走完整 6 阶段 |
| 重构 | 推荐 — 走完整流程，阶段 2 侧重风险评估 |
| Bug 修复 | 简化 — 跳过阶段 1、2，直接 TDD + 审查 + 提交 |
| 单文件小改 | 不建议 — 直接改 + 审查即可 |
| 纯研究/调研 | 不适用 — 无代码产出 |

---

## 反模式警示

- **不要跳过门禁** — 用户确认是安全阀
- **不要忽略审查结果** — CRITICAL 级别问题必须修复
- **不要用一把梭处理模糊需求** — 阶段 0 没搞清楚就往下走
- **不要并行执行有依赖的阶段** — 架构方案没出来就 TDD 无意义
